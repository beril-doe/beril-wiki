Concept Consolidation

The wiki claimed to be synthesis, but 136 of its 153 concept pages cited a single project — a restated summary wearing a concept title. This stage merges the duplicates and back-fills cross-project evidence, and it runs as part of the ordinary pipeline.

The problem

A concept page that cites one project is just a summary with a different title

The defect was structural, not a bug. stages/enrich.py creates concepts one document at a time and hard-codes a single-element sources list. compiler.py merges a document into pages only when that document changes. So a concept created from document #60 was never revisited against documents #1–59 — nothing in the pipeline ever looked backwards.

The existing duplicate detector could not see it either. wiki_check.duplicate_concepts requires ≥50% source-set overlap between two pages; single-source pages can only clear that bar by sharing their one identical source. It found 3 pairs in the whole corpus.

What was built

One new stage, slotted between enrich and conflicts

src/beril_wiki/stages/consolidate.py reuses compiler.py's machinery — the same generate_page call, so write-time validation, the one-retry path, frontmatter handling and index maintenance are identical to every other page write in the wiki. No new dependency.

01fetch 02compile 03enrich 04consolidate ← new 05conflicts 06hubs 07literature 08figures 09extras 10authors 11check 12publish

It runs after enrichment creates concepts and before anything downstream reads the concept layer, so hubs and conflict pages are built from the consolidated set.

Step 0 — index every page

Each concept page yields four things, all derived from the prose rather than the frontmatter: cited, the project ids inside real [src:] tags; nums, every figure in the body, normalised; etext, the slug + description + whole body for embedding; and a content digest for the cache.

Every pair must share a cited project, share ≥3 exact figures, and reach numeric-set Jaccard ≥ 0.5.

B · Embedding rank recall net

Two models embed every page; each contributes its own top-45 by cosine. Ranked by the best rank any model gave the pair — not a shared cosine cutoff, because ranges differ per model.

catches paraphrases sharing no numbers

Phase 1 · merge per pair, in rank order

  1. Re-key through the redirect map if a side was already merged away
  2. Skip if either file is gone, or the pair sits in the rejected cache
  3. gate re-check both-mature against the live pages — a redirect can turn a legal pair into a hub-into-hub merge
  4. One judge call: both bodies, each page's cited projects, and their intersection
  5. On merge, one generate_page rewrite of the survivor
  6. gate citation retention — every [src:] id from both inputs must survive; else one retry, else the merge is abandoned and both pages kept
  7. Write survivor with the union of both sources; delete the loser; repoint every [[concepts/loser]] and [[concepts/loser|alias]] across wiki/ and wiki/

re-embed if anything merged — page content changed, so similarity did too

Phase 2 · back-merge per thin concept

  1. For each concept citing <4 projects, take its top-2 summaries above cosine 0.78 that are not already in sources
  2. Run compile's existing CONCEPT_UPDATE_USER, plus a tail offering an explicit UNCHANGED reply
  3. gate citation retention, as above
  4. gate anti-padding — if the reply is UNCHANGED, or the new project id never appears in a real [src:] tag, the whole rewrite is discarded and the page left untouched
  5. Otherwise write, extending sources by exactly that one summary

Why the anti-padding gate exists

The previous-generation corpus looked multi-source but padded frontmatter with bare "See also" links on 60 of its 81 concept pages — 65% of its concept bodies cite exactly one source. Chasing its numbers would have copied its defect, so sources can only ever grow alongside a real citation in the prose.

What the state file holds

Only negatives — rejected and no_evidence, keyed by prompt version plus both content digests, so an edited page or a changed prompt is re-asked rather than inheriting a stale answer. Positives need no cache at all: a completed merge is a missing file, and a completed back-merge is a summary already listed in sources.

The correction

The first version found almost nothing, and the cause was the representation

Candidate generation originally ranked pages by embedding similarity. To test whether that worked, ground truth was built without embeddings: single-source concepts sharing their one cited project, narrowed to pairs whose bodies restate near-identical numbers — the objective signature of a restated shard.

What the measurement showed

The shipped representation surfaced none of them. Median rank 624 of 7,381 pairs; recall at the stage's own cut-off was 0 of 8. A pair citing identical number sets sat at rank 3016 with cosine 0.677 — below the corpus median.

The cause: load_concepts embedded body.split("\n## ")[0] — the lead paragraph only — discarding every evidence section, which is exactly where the shared figures live.

The bigger lesson: don't proxy what you can measure directly

Even after the fix, embeddings find only a minority of duplicates. The defect is "two pages restating one study's measurements", so the stage now detects that directly: pages sharing a cited project and three or more identical figures, at a numeric-set overlap of 0.5 or higher. That yields 20 pairs out of 7,381 — deterministic, free, and containing every known duplicate. Those are judged first; embeddings still contribute paraphrases that share no numbers.

The effect on precision was immediate: the merge judge accepted 15 of 17 candidates on the first run after the change, against roughly 40% for embedding-only candidates.

Reproducibility

Yes — it is a stage, not a one-off script

It is wired into scripts/run_pipeline.sh and obeys the same contract as every other stage: hash-cached, idempotent, resumable, and a no-op when nothing changed. Running the pipeline on an unchanged corpus still costs $0.

# the whole pipeline — consolidation runs in its normal slot
CBORG_API_KEY=... scripts/run_pipeline.sh

# just this stage, and see the candidates before spending anything
uv run python src/beril_wiki/stages/consolidate.py --dry-run     # $0 — no LLM calls, no writes
uv run python src/beril_wiki/stages/consolidate.py               # the real run

# the runnable check that ships with it
uv run pytest tests/test_consolidate.py
  • A $0 dry run comes first. --dry-run embeds, ranks and prints both candidate lists with their scores, making no LLM calls and no writes — so candidates can be eyeballed and thresholds picked from data before any spend.
  • Re-running is safe. A completed back-merge shows up in sources and a completed merge shows up as a missing file, so both are skipped for free. Only negative verdicts need state, in state/consolidate.json, keyed by page digest and prompt version so an edited page or prompt is re-asked rather than silently inheriting a stale answer.
  • It converges over passes rather than in one. Merging changes page content, which changes what looks similar next time. Four passes were run here; each is cheaper than the last.
  • Spend is bounded and tunable. COMPILE_BUDGET_USD aborts before overrun, and --merge-topn, --backmerge-threshold, --topk, --min-sources and --evidence-jaccard control how aggressive a run is.
  • The budget tripwire under-counts. One pass self-reported $0.80 while the gateway billed $1.29 — reasoning tokens appear to be billed but absent from the reported completion count. Treat it as a guard rail, not a ceiling; real spend is readable from the gateway's /user/info.

Known debts

What is still open

  • 15 concepts still cite one project. Some have no similar summary at any threshold — genuinely single-project ideas. Forcing evidence into them is the padding the stage exists to prevent.
  • The entity layer has no duplicate detection at all. 336 pages, and duplicate_concepts scans only concepts — while the editorial contract requires one page per real-world entity with aliases and external ids. egg-nog and eggnog are two pages for one tool.
  • Hub and conflict stages skip two validators that compile pages get: the numeric check and wikilink-target validation. They use their own untracked LLM call rather than generate_page, so a few dead links reach those pages and are stripped at publish.
  • conflicts_build never reaps stale pages the way topics_build does. One fully-orphaned conflict page exists today.
  • Four pages list a source their body never cites — pre-existing, from compile and enrich rather than this stage, which cannot add one.
