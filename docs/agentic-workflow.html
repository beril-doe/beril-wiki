    The agentic wiki workflow

    A fixed Python schedule drives subscription-backed writer and reviewer jobs that update the wiki. Every derived page receives its complete evidence in one prompt, is checked by code before a one-turn review, and is corrected by paragraph patches. Python keeps the work bounded, reviewable and recoverable.

    A fixed schedule runs stale stages; Python controls acceptance

    The Claude Agent SDK uses the maintainer's subscription for model jobs. The runner integrates changed sources first, then runs conflicts, topics, literature and authors whenever their input or output fingerprints are stale, writing a receipt of changed paths per stage inside an isolated candidate workspace. No model chooses the order.

    The model still plans page integration and proposes topic membership. Python retains the acceptance rules; arbitrary shell commands and changes to those rules are outside any job's tools.

    The dependency table is the schedule

    Follow one changed report through integration
    1. Extract exact quotes and offsets from overlapping ranges across the whole report, including caveats and null results.
    2. Plan coverage for every evidence record and combine changes by destination page.
    3. Write anchored patches or justified rewrites. Integration writers may retrieve source passages; derived-page writers get their evidence packed instead.
    4. Check structure, links, citations, quantities and retained evidence, including evidence from absorbed pages.
    5. Run a separate scientific review for support and lost meaning, then resolve entities and refresh metadata.

    Python applies existing human concept decisions before the schedule, then handles final naming, figure placement and strict validation afterward. Figure selection still uses accounted model jobs. Quartz builds from the accepted output in a separate step.

    Follow one derived page from evidence pack to acceptance
    1. Code packs the evidence: the tension paragraph with its tags, concept leads and the source paragraphs stating its figures for a conflict; member concept pages and linked conflict leads for a hub; abstracts for a literature section; summaries for an author.
    2. The writer receives the stage's rule list and the pack, and answers in one turn with no tools.
    3. Gates run in code: length, required headings, preamble, figures absent from the input, invalid tags, uncited or unsupported figures. Dead links and legacy platform names are repaired in code.
    4. The reviewer receives the same rules and pack plus the numbered candidate and returns one JSON verdict of paragraph-indexed issues.
    5. A rejection is patched by paragraph index against a base hash; only the replaced paragraphs are reviewed again. Two rounds, each seeing the latest verdict.
    6. A page that has not converged keeps its previous version and is listed in the run summary and .agentic/failures.json; the stage continues.

    Cached work and targeted context limit repeat inference

    The shared ledger records raw generation, review, patch and provider cache tokens and admits on an effective figure (cache writes at 1.25, cache reads at 0.1). It reserves headroom for every job in flight. The configured token budget and an optional per-stage ceiling control admission; an in-flight job can exceed its reservation, after which new jobs stop. Killed jobs are charged from their transcripts automatically. These counts do not report remaining subscription allowance.

    Tools and limits available to model jobs
    • Only integration jobs have tools: read_evidence for extraction and its review; planners and page writers also get literal search_evidence, and page writers validate_candidate. Its feedback does not replace final host validation or scientific review.
    • Derived-page writers, patchers and reviewers have no tools and one turn; their evidence arrives packed in the prompt.
    • Default limits are 12 turns per tool-using job, 600 seconds per job, four hours per stage and four page workers. A page needs at most six jobs.
    • The runtime checks direct subscription authentication and removes inherited API routing. This path uses no embedding API. PubMed remains an external data source.
    Choose models by job role

    The committed agentic.yaml is loaded automatically. Opus 5 handles extraction, planning, writing and scientific review. Sonnet 5 handles literature queries and figure selection. This policy protects scientific fidelity while assigning bounded selection tasks to Sonnet; it has not yet been benchmarked on the corpus.

    Use --model-config PATH for a replacement policy or --step-model ROLE=MODEL_ID for an individual override. --model MODEL_ID replaces the whole policy with one model before individual overrides apply. The CLI prints the resolved policy; token and job ceilings remain explicit run flags.

    Repairs and paragraph patches retain their role's model; separate reviews use the review model. Every role shares the ledger and budget, and changing models on the same interrupted input snapshot preserves earlier charges. Jobs record their configured model, and accepted state records the complete policy. Cache invalidation follows the affected roles. See the model-routing guide for details.

    Failed work stays inspectable without replacing the wiki

    A capped real-source update remains the acceptance step

    Recorded-response tests exercise the pipeline, cache reuse, dependencies, gates, patches, recorded failures and recovery. They do not establish scientific quality. The first derived-prose adoption ran live on 2026-09-15/16 with zero changed sources; a real source update has not yet been accepted.

    The implementation lets the model write, review and organize knowledge under a fixed schedule. Its domain operations and mandatory checks remain deliberate boundaries. Read-only wiki search is available as a CLI; BERIL or OpenViking integration has not been installed.

    Start with uv run python -m beril_wiki.agentic plan to inspect staged changes without inference. Use the operating guide for run budgets, status, retry and recovery commands. Local promotion leaves committing, pushing and publishing as separate actions.
