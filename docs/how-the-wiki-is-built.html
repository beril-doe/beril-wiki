    How the BERIL wiki is built

    Seventy-five research reports from the observatory become a wiki of 667 pages through one command that runs fourteen stages. Each report is summarised, then merged into every concept and entity page it changes, and each page is checked against the sources it cites before it is written. The knowledge graph is no longer built first. It is read out of the finished pages, from their citations and links, and used to cluster concepts into topic hubs. That inversion is what makes the pipeline incremental rather than byte-reproducible.

    One command runs fourteen stages, and every stage skips what has not changed

    The first build and every later addition use the same command. Each stage hashes its inputs and does nothing when they are unchanged, so an interrupted run resumes where it stopped and a rerun on a finished corpus makes no model call. The stages fall into six phases.

    Step one turns a report into a summary, then rewrites the pages it touches

    Reports are processed one at a time, oldest first. Nothing is filed under the report. Instead the report changes the wiki: a few concept pages gain evidence, a few entity pages gain facts, and each of those pages is rewritten in full so the new evidence sits next to the old with its relation stated in words.

    The summary is dense and keeps every number exactly as the report states it. Its closing Slots Into section names the concepts the findings feed. The plan is one model call. Code builds its input from frontmatter: one line per existing concept and entity with its one-sentence description, plus the duplicate audit. The model returns JSON naming which concepts and entities to create, update, or merely link, and code performs every write. Concept and entity pages are first created here, not in a later stage. A create must argue why no existing page covers the idea, and the plan is told to prefer updating. A merge-rewrite must preserve every existing claim, number, and citation, must say whether new evidence supports, contradicts, or refines what is already there, and must record a disagreement under a Tensions heading rather than resolve it. A page that already lists the report among its sources is skipped, so a run interrupted mid-report resumes at page granularity.

    A page is checked against its sources before it is written, not after

    The previous compiler wrote pages and then warned. This one refuses the page. Three checks run on every generated page, and the same checks now also cover hubs, conflicts, and author pages, which used to be written unchecked.

    The numeric check is narrow. It confirms that a figure occurs in a cited source as text. It cannot see a flipped sign, a changed unit, a wrong denominator, or a figure attached to the wrong claim, and nothing in the pipeline checks whether a finding is correct. The About page on the site says this in the same words.

    The concept layer is grown, then consolidated, so pages argue across projects

    Compile alone under-built the synthesis layer: the bulk model created nineteen concepts where the reference corpus had eighty-one. Two stages fix that from opposite directions. Enrichment adds concepts with a deliberately pro-creation prompt, one summary at a time; it only creates and never compares pages to each other. Consolidation is the first stage that does compare, and it merges the near-duplicates that per-document creation produces and back-fills evidence from other projects into thin pages.

    Consolidation finds candidate pairs three ways, most precise first: pages that restate the same figures from a shared project, pages built from an identical set of cited projects, and finally an embedding ranking as a recall net for paraphrases that share no numbers. One model call judges each pair on the evidence it rests on rather than its framing. A merge rewrites the survivor through the same validated path compile uses, deletes the loser, and repoints every inbound link in code. Two gates hold after the model replies: no citation and no figure present in either input may be missing from the output, and a page's source list may only grow together with a real citation in its prose. Pairs where both sides are already mature are refused by design; those need a person, and the answer is recorded in contract/concept-decisions.yaml and reapplied on every run. Today 12 of the 92 concepts still cite one project, and some are single-project ideas that should stay that way.

    The knowledge graph is read out of the pages, and it is what makes the topics

    There is no graph file. The pages carry the graph: every citation tag is an edge from a page to a project, and every wikilink is an edge from a page to a page. The hubs stage materialises that graph over the concept pages only, as an in-memory networkx object, clusters it, hands each cluster to the model as the context for one topic hub, and discards it. Summaries, entities, and hubs are not nodes.

    The hub prompt receives the member concept pages and nothing else, and may cite only project ids those pages already cite. Only hubs whose member set changed regenerate. The home page is one call to a stronger model, since it is the page every reader lands on. The same page-level graph is read three more times downstream.

    Publishing renders committed pages, and the deploy repeats the checks

    The corpus, its source reports, and all 654 figure files are committed, so the site is a rendering of the repository and needs no gateway key. Refreshing content is still a maintainer running the pipeline locally and committing the result.

    Ingest is where the reader's view diverges from the corpus. Citation tags turn into links to summary pages, and summaries link their raw reports. Entity pages that cite one project are omitted and their inbound links become plain text. Figure placements chosen by the figures stage are spliced in, with 227 placements across summaries, hubs, and conflicts. A placement is a paragraph position and a file name in a state file, so no placeholder is ever written into the corpus and no page is rewritten to receive a figure. Every page gets a callout under its title saying the wiki is AI-generated and partially reviewed, with the computed evidence terms where the page has any.

    The compendium built the graph first; the wiki builds pages first and derives the graph

    The compendium of June 2026 extracted statement cards from each report, reconciled their topic and entity slugs into one registry, planned pages deterministically from cards plus registry, and had a model write each page from its plan. The registry was the knowledge graph, and it was the backbone. The current pipeline reverses the order.

    Three ideas from the compendium survived the change. Typed relations became the supports, contradicts, and refines vocabulary the merge prompt requires. Write-time citation whitelists became the validator. The deterministic connectors for authors and shared data became the extras stage, still without a model. What was given up is the exact quoted span per statement, byte-level reproducibility, and a graph that could be exported as triples. The evaluation of an external graph framework in early September reached the same verdict: if a queryable graph is ever needed, derive it from the pages rather than compile the pages from it.

    What is reproducible now is the set of guarantees, not the bytes

    Model calls run at low temperature but are not deterministic, and reports are merged in order, each into the wiki as it stood at that moment. A rebuild from an empty wiki therefore yields the same kind of wiki with different sentences. What a rerun does depends on what changed.

    That last row is the practical answer. Because the compiled corpus is committed, the artifact anyone sees is reproducible by checkout rather than by regeneration, and the CI gate verifies the invariants on every push. The price of incrementality is that two people rebuilding from scratch would get two different wikis that pass the same checks. The compendium paid the opposite price: identical bytes, and eight projects it never integrated.

    The backbone is the page set on disk, and no model call sees more than a slice of it

    The compendium's backbone was its registry, an explicit graph file that page planning read. Now the backbone is the concept and entity pages themselves. Each carries frontmatter naming its type, its description, and the summaries it integrates, and its body carries the citation tags. "Which projects feed which concepts" is answered by scanning those, an inverted index rebuilt in code on every run rather than stored. Everything is committed: the pages, a code-generated index page listing every page with its description, the source reports, the figures, and the state directory of hashes, cached verdicts, placements, and topic names. Nothing graph-shaped is stored, and nothing lives outside the repository.

    The limit that binds first is not the model's window. Merges re-emit whole pages, and the pipeline refuses a reply that hits its own output cap as truncated. That cap is a constant and can rise toward the models' 128K, but the underlying cost is the whole-page rewrite, which is the sectioned-append ceiling already marked for around five hundred reports. The plan index reaches a 1M window only past several thousand reports; well before that its quality is the concern, since a planner choosing from thousands of one-line briefs chooses worse. The fix when it is needed is retrieval, embedding the briefs and passing the relevant few dozen, and the embedding machinery already exists in consolidation. Neither is a problem today.

    Known limits, stated as the site states them

    • No one has reviewed the pages themselves. Scientists have checked some of the underlying research; the site does not mark which claims fall on which side, and every page says so.
    • The numeric check confirms presence in a source as text. Units, signs, denominators, and whether a figure attaches to the right claim are unchecked.
    • The spend tripwire undercounts by about half, because reasoning tokens are billed but not reported. Real spend is read from the gateway.
    • Merging two mature concepts needs a person. Four such pairs were read and decided by hand; the decisions are in the repository and reapply on every run.
    • The conflicts stage never retires a page whose tension has disappeared, and the checker does not scan that collection.
    • Hot pages are rewritten in full on every merge, so per-report cost grows with page size. Sectioned appends are the marked upgrade past about five hundred reports.

    3. Follow the tag to a concept page. Show a bolded supports or refines, the Tensions section, and Open Directions.
    4. Open a conflict page from the hub and show Evidence Sides and Resolving Work.
