# Spark query scale limits and notebook-session constraints in Lakehouse analyses

This page covers Spark query scale limits and notebook-session constraints in Lakehouse analyses.

## Literature Context

The candidate papers are tool papers. They describe Apache Spark libraries for biological data, and they say little about the failure modes this page documents. DIAMIN is a Java library built on Spark for large-scale molecular interaction networks. Its abstract reports that it was tested on data from two widely used interaction databases and was "highly efficient and scalable" [PMID 36368948](https://pubmed.ncbi.nlm.nih.gov/36368948/). scSPARKL applies Spark to single-cell transcriptomics. It covers data reshaping, preprocessing, cell/gene filtering, normalization, dimensionality reduction and clustering, and its abstract claims it can analyze scRNA-seq datasets "of any size" [PMID 40731055](https://pubmed.ncbi.nlm.nih.gov/40731055/). Thunder, a Spark library for neural imaging data, reports analyses that "run in minutes or less" on a private cluster or in the cloud [PMID 25068736](https://pubmed.ncbi.nlm.nih.gov/25068736/). PyBDA runs on Spark and uses Snakemake to schedule jobs on a high-performance computing cluster. The authors demonstrate it on image-based RNA interference data from 150 million single cells [PMID 31718539](https://pubmed.ncbi.nlm.nih.gov/31718539/). Avishkar uses a distributed kernel SVM with a Spark backend for miRNA target prediction, and all of its pipeline operations are described as distributed [PMID 29993641](https://pubmed.ncbi.nlm.nih.gov/29993641/). These abstracts are not full text. They report scalability as a design aim and a demonstration. They do not describe driver result-size caps, session timeouts or type conversions.

CloudDOE is a looser fit. It deploys Hadoop clouds for MapReduce sequencing applications and mentions Spark only as possible future support [PMID 24897343](https://pubmed.ncbi.nlm.nih.gov/24897343/). It is background on cluster deployment and does not bear on Spark scalability.

The literature abstracts do not state a strategy of filtering and aggregating in the cluster. That advice comes from this page's own reports. They say to filter, join and aggregate in Spark before calling .toPandas(), to compute Fisher contingency counts server-side, and to stage large results through MinIO parquet. The tool papers are consistent with this only loosely. Their pipelines are distributed from end to end, and their abstracts do not discuss collecting results to a single driver. The corpus's 1 GB serialized result cap, the pandas explode and merge blow-ups, the idle kernel kills after ~17–25 minutes and the DECIMAL and ChunkedArray conversion problems are not addressed by any candidate. They extend the published picture with operational detail and are novel relative to these papers.

The corpus does not contradict these papers, but it qualifies their scalability claims. On the KBase Data Lakehouse, a Spark query can succeed and the analysis can still fail when the result is collected to the driver, or when a notebook session is killed. The corpus's autoBroadcastJoinThreshold tension, the 8% gain from BROADCAST hints and the unpartitioned billion-row scans are practical tuning observations with no counterpart in the candidates. This section cannot compare them with the literature, because no candidate abstract reports comparable measurements.

## Driver result-size caps and large joins

Several projects hit driver result-size failures. Spark Connect has a driver result-size cap of 1 GB serialized, and the report's workaround is to stage through MinIO by writing parquet and reading it locally. [src: gene_function_ecological_agora] The cap was reached when joining 1B-row tables filtered to more than 200K elements. [src: gene_function_ecological_agora] In the Bacteroidota PUL (polysaccharide utilization locus) scan, even a canonical-only set of 2 KOs (KEGG orthologs) gave 723K focal features × 210K contigs and a 1.3GB serialized result that exceeded spark.driver.maxResultSize. [src: gene_function_ecological_agora] The report presents these lessons as reusable for projects with 1B-row table joins, 28M-row species-level data and 17M event attribution. [src: gene_function_ecological_agora]

The pitfalls digest describes the same failure. Calling .toPandas() on a Spark Connect join of 1B-row tables filtered to >200K elements via broadcast hits spark.driver.maxResultSize = 1024 MB and raises a serialized-result-size error. [src: pitfalls] The cap cannot be raised with SET spark.driver.maxResultSize at runtime, because the property is read-only after session start. [src: pitfalls] The workaround is to write the result as Parquet to MinIO and read it back with spark.read.parquet(path).toPandas(), which goes through Spark Connect's Parquet streaming path and avoids the cap. [src: pitfalls] Reading with pyarrow.parquet.read_table(path) through s3fs is an alternative if pyarrow is configured. [src: pitfalls] The illustrative scale is 218K Bacteroidota contigs × ~140 features/contig = 30M+ rows × ~50 bytes serialized ≈ 1.5 GB. [src: pitfalls] The report calls this a standard pattern for genome-context cross-walks at >200 species. [src: pitfalls]

Other projects hit the same cap. In ecotype_env_reanalysis, extracting Klebsiella pneumoniae gene-cluster memberships (250 genomes × ~5,500 genes per genome) via a gene JOIN gene_genecluster_junction exceeded the 1GB default spark.driver.maxResultSize. [src: pitfalls] The query succeeds in Spark but fails when collecting results to the driver. [src: pitfalls] For species with >200 genomes, the report recommends chunking the genome list into batches of 50-100 and concatenating, or increasing spark.driver.maxResultSize in the session config. [src: pitfalls] The per-species extraction script catches this error with try/except and continues to the next species. [src: pitfalls] In plant_microbiome_ecotypes, collecting species×OG (ortholog group) matrices from the 93M row eggnog_mapper_annotations table can exceed spark.driver.maxResultSize (1024 MiB). [src: pitfalls] The report recommends computing Fisher test contingency counts server-side in Spark SQL and collecting only summary counts. [src: pitfalls]

More generally, .toPandas() pulls all data to the driver, which is slow for large results and can exhaust memory, so filtering, joins and aggregations should be done in Spark first. [src: pitfalls] The report recommends PySpark DataFrame operations for intermediate steps and .toPandas() only for local plotting, CSV export, or results of a few thousand rows. [src: pitfalls] In the presence-matrix profiling, .toPandas() on 1-2M result rows took <2s and was not the bottleneck. [src: pitfalls]

Joins that touch kbase_uniprot.uniprot_identifier, a 2.5B-row table, can exceed spark.driver.maxResultSize (1GB) through broadcast exchange. [src: discoveries] The discoveries digest recommends SET spark.sql.autoBroadcastJoinThreshold = -1 to force sort-merge joins. [src: discoveries] The agora report **limits** this as a general default. In its NB10, setting the threshold to -1 hung the notebook for 17+ min until the setting was removed. [src: gene_function_ecological_agora] The pitfalls digest gives the same case: the setting was a defensive default carried over from prior projects, and it hung an NB10 KO atlas job for 17+ minutes on a 13.7M × 18K join. [src: pitfalls] The job waited for a shuffle that never materialized, and the 18,989-row species_tax table was below the default 10MB broadcast threshold and would have been auto-broadcast at default settings. [src: pitfalls] The report recommends removing the disable, trusting the optimizer for small-table joins, and using explicit F.broadcast(small_df) hints when it does not auto-detect. [src: pitfalls] Its general rule is that copied defensive Spark configuration can be counterproductive and should be audited. [src: pitfalls] The same agora report lists "autoBroadcast harmful-default" among its documented caveats. [src: gene_function_ecological_agora]

Explicit broadcast hints on small filter tables worked in another project. They cut presence-matrix queries, which join two billion-row tables, to ~210s per organism. [src: cofitness_coinheritance] The Smeli profiling (241 genomes, 6K target clusters) gives the comparison: extraction without BROADCAST took ~300s per organism [src: pitfalls], and BROADCAST hints on the filter tables took ~274s, an 8% improvement. [src: pitfalls] A two-stage approach, filtering the junction first and then looking up genome_ids, took ~310s with no improvement. [src: pitfalls] For billion-row pangenome joins, the report recommends registering target cluster and genome IDs as temporary views and using BROADCAST hints on both filter tables. [src: pitfalls] It also recommends caching extracted presence matrices as TSV files to skip extraction on reruns [src: pitfalls], setting ExecutePreprocessor.timeout=3600 for nbconvert --execute [src: pitfalls], and budgeting ~5 min per organism, so 11 organisms ≈ 55 min total. [src: pitfalls]

Other large-table cautions:
- The NMDC kraken2_classification_report table has ~29M rows. Aggregate each classifier to one row per workflow_run_id before joining metadata, and never scan it unfiltered. [src: euk_in_prok_correlates]
- One Spark query exploded eggNOG_OGs annotations across 93.5M gene clusters and matched every comma-separated entry against 11,774 dark gene root ortholog groups. [src: functional_dark_matter]
- An 833M-row scan over the full 10,750-KO scope was infeasible through Spark Connect in practical time. The project rescoped to focused subsets. [src: gene_function_ecological_agora]
- Joining gene_genecluster_junction (~1B rows) with gene (~1B rows) to build genome × cluster presence matrices takes 3-5 minutes per species, because neither table is partitioned by gene_cluster_id or genome_id and every query needs a full scan. [src: pitfalls]
- The gene and gene_genecluster_junction tables are unpartitioned parquet. Partitioning by genome_id and gene_cluster_id respectively would dramatically reduce scan time but requires rebuilding KBase Data Lakehouse tables. [src: pitfalls]
- Spark LIMIT N OFFSET M pagination re-scans all rows up to the offset on each query. [src: pitfalls] In conservation_vs_fitness, extracting cluster representative FASTAs across 154 clades with paginated queries of 5000 rows per batch was orders of magnitude slower than single queries per clade. [src: pitfalls] Since gene_cluster is partitioned by gtdb_species_clade_id, a single filtered query per clade is fast, and the report recommends paginating only when results would exceed memory. [src: pitfalls]
- Pagination requires ORDER BY, because LIMIT/OFFSET without ordering returns inconsistent results. [src: pitfalls]
- In enigma_contamination_functional_potential, separate heavy Spark joins and aggregations over eggnog_mapper_annotations for each mapping mode can stall notebooks on large tables. [src: pitfalls] Precomputing per-clade total, defense, mobilome and metabolism annotation totals and deriving genus feature fractions in pandas preserves mapping-mode independence while reducing duplicate Spark work. [src: pitfalls]
- The report recommends direct cluster spark.sql() for pangenome queries over >1M rows, large-table joins, billion-row aggregations, or repeated REST API timeouts. [src: pitfalls]
- In cog_analysis, joining gene through gene_genecluster_junction and gene_cluster to eggnog_mapper_annotations can be slow for species with >500 genomes. [src: pitfalls] The report suggests direct Spark on JupyterHub, separate queries per gene class, or species with 100-300 genomes. [src: pitfalls]
- For best pangenome query performance, use exact equality rather than LIKE patterns. [src: pitfalls]
- Querying ANI (average nucleotide identity) for all 13K+ genomes in one IN clause fails or times out, so ANI must be queried per species. [src: discoveries] Per-species IN-clause queries scaled to ~5,000 genomes per species on the JupyterHub Spark Connect kernel. [src: gc_ecotype_ecology] They ran in seconds for typical species of 50–500 genomes and in seconds-to-a-minute for a 5,000-genome Staphylococcus aureus subsample. [src: gc_ecotype_ecology]
- In amr_strain_variation, ANI queries for species with >500 genomes can take 30+ minutes per species and may time out Spark connections. [src: pitfalls] K. pneumoniae (14,240 genomes) and S. aureus (14,526 genomes) generate IN clauses with 14K+ IDs that overwhelm the query planner. [src: pitfalls] For ANI-based Mantel tests the report recommends capping at <=500 genomes or subsampling. [src: pitfalls]
- Pulling all of alphaearth_embeddings_all_years (83K genomes × 65 columns) into pandas finished in under a minute. [src: gc_ecotype_ecology]
- The pangenome REST API can return transient 503 ("cannot schedule new futures after shutdown") and 504 errors on large queries, for which the report recommends retries or per-species batches. [src: pitfalls]

## Pandas memory limits and explode blow-ups

Collecting is not the only limit. Pandas spatial-range merges ran out of memory at ~10M+ rows and need batching. [src: gene_function_ecological_agora] Sampling 309 random Bacteroidota species still gave a Stage 6 merge of ~24M rows × 9 cols, and the 9GB DataFrame ran out of memory. [src: gene_function_ecological_agora] The full-scale pipeline hit the same out-of-memory failure at 723K focal features × 210K contigs, which deferred the PUL and mycolic neighborhood analysis. [src: gene_function_ecological_agora] For work beyond ~20K focal features × ~20K contigs, the report recommends full-Spark spatial filters that collect only per-feature aggregates, or batched MinIO-staged processing. [src: gene_function_ecological_agora] The default driver heap ceiling was -Xmx4g, and the report recommends raising it through the environment for heavy coalesce writes. [src: gene_function_ecological_agora] Workers and driver on that setup share no filesystem, so atlas-scale parquets stay MinIO-only. [src: gene_function_ecological_agora]

The pitfalls digest explains the mechanism. After Spark filters to focal features, the in-pandas spatial-range merge of focal and contig features on contig_id, then filtering by ±NEIGHBOR_BP, is a Cartesian-product-then-filter pattern. [src: pitfalls] For 80K focal × 21K contigs × ~105 features/contig avg, the merged frame was ~24M rows × 9 columns ≈ 9 GB, which exhausted a 16 GB driver. [src: pitfalls] In NB26h, 723K focal × 210K contigs failed, and sampling to 309 species still ran out of memory at 80K × 21K. [src: pitfalls] The fixes are to process focal features in batches of ~10K and accumulate aggregates [src: pitfalls], or to push the BETWEEN filter into Spark and collect only per-feature aggregates. [src: pitfalls]

Row-wise Python loops are also slow. In NB26e Stage 6, iterrows with a per-row groupby lookup over 27K focal features × 218K contigs ran 30+ minutes without finishing. [src: pitfalls] A vectorized pd.merge on contig_id followed by a boolean filter did the same operation in ~10 seconds. [src: pitfalls] In core_gene_tradeoffs, filtering a 961K-row DataFrame with row-wise apply for orgId/locusId set membership was extremely slow, and an inner merge gave the same result in seconds instead of minutes. [src: pitfalls]

Explode can blow up as well. In NB28b, exploding 6.3M gain events × ~20 candidate-donor genera per event gave a 126M-row DataFrame of ~19 GB and exhausted memory. [src: pitfalls] An algebraic replacement using a single join and subtraction let Stage 2b run in 142s. [src: pitfalls] The general rule is to look for sum-over-bins reformulations when an explode produces O(N×M) rows with bounded but large M. [src: pitfalls]

## Cluster load and session timeouts

Query time varies with cluster load. Per-species queries took 94s–1642s during heavy usage, and 2 species were lost to S3 read errors. [src: ecotype_functional_differentiation] That load limited the sample to 15 species, and the report proposes scaling to all 456 eligible species off-peak or with optimized queries. [src: ecotype_functional_differentiation]

Long sessions are also killed. Long-running Python processes on one JupyterHub were silently killed after ~17–25 min, with no error message. [src: gene_function_ecological_agora] The pitfalls digest reports the same: kernels idle-time out after ~17–25 minutes without user activity, silently killing cells such as 30+ min Spark jobs or NB10b M22 attribution at 17M events. [src: pitfalls] The report judges this consistent with a scheduler or session timeout rather than code errors. [src: gene_function_ecological_agora] Running [[entities/jupyter-nbconvert]] with --execute on notebooks that call spark.sql(...).toPandas() on large results kills the kernel with DeadKernelError. [src: discoveries] Long-running notebooks run with nbconvert may also time out, so set --ExecutePreprocessor.timeout appropriately. [src: pitfalls] Workarounds:
- Convert the notebook to a plain .py script (for example with jupytext) and run it with nohup python3 -u from a terminal, which removes ipykernel buffering. [src: gene_function_ecological_agora, pitfalls]
- Add cache-check logic to Spark cells so nbconvert can run locally from cached CSVs. Capture live Spark outputs interactively. [src: discoveries]
- Run long Spark-query scripts outside nbconvert. [src: ecotype_functional_differentiation]
- Save intermediates after each stage with direct pd.to_parquet. [src: gene_function_ecological_agora]
- Write small files before large parquets, because the kill seems to fire mid-write on the largest parquet. [src: gene_function_ecological_agora]
- Write intermediate parquets at each stage and provide _finalize.py recovery scripts that load them and finish the killed run. [src: pitfalls]
- Design long pipelines with checkpointing, skipping steps that already have output. [src: pitfalls]

The agora report calls this pattern reliable despite its extra complexity. [src: gene_function_ecological_agora] The get_spark_session import from berdl_notebook_utils.setup_spark_session works in regular scripts on JupyterHub, so full pipelines can run from the command line. [src: discoveries] The notebook auto-import affects only notebook kernels. [src: discoveries]

### Spark Connect session fragility

- A Spark temporary view may be silently destroyed if Spark Connect reconnects during a cell, for example during an expensive 305M-row full-table scan, in nmdc_community_metabolic_ecology. [src: pitfalls] Later cells joining against the lost view return 0 rows with no error. [src: pitfalls]
- The report recommends re-registering the view immediately before any join cell, because the Python data variable persists through reconnections. [src: pitfalls] It also advises avoiding expensive scans between registration and use, and using LIMIT or TABLESAMPLE rather than full GROUP BY counts for schema checks on large tables. [src: pitfalls]
- Spark Connect runs as a Java process on port 15002 (conservation_vs_fitness). [src: pitfalls] Killing Java processes, for example when cleaning up stale notebook processes, takes down Spark Connect, and get_spark_session() then fails with RETRIES_EXCEEDED or Connection refused. [src: pitfalls]
- Recovery means logging out of JupyterHub, starting a new session, and running get_spark_session() from a notebook. The daemon cannot be restarted from the CLI. [src: pitfalls]
- Rarely accessed databases, including phagefoundry_strain_modelling, need Spark warm-up. /count may return correct results while /query and /sample return 0 rows or empty results. [src: pitfalls] The workaround is to verify with /count, then retry /query with exponential backoff, which may take several minutes. [src: pitfalls]
- Local Spark Connect setup, .venv-berdl activation and kernel-restart retry patterns are documented in .claude/skills/berdl-query/references/off-cluster-mechanics.md. [src: pitfalls]

### get_spark_session import patterns

The import pattern differs across three environments, and the wrong one causes an error. [src: pitfalls]
- In JupyterHub notebooks, get_spark_session() needs no import, because /configs/ipython_startup/00-notebookutils.py injects it. [src: pitfalls]
- In JupyterHub CLI scripts, import it from berdl_notebook_utils.setup_spark_session. fitness_modules found this works in regular Python scripts. [src: pitfalls]
- On a local machine, use from get_spark_session import get_spark_session. [src: pitfalls]
- That local import on the cluster causes ImportError, since the module is local-only. [src: pitfalls] The cluster import locally causes ImportError, since the package exists only on the cluster. [src: pitfalls] A bare get_spark_session() in a CLI script causes NameError, since auto-import applies only to notebook kernels. [src: pitfalls]

## REST API failures

Prefer direct Spark SQL via get_spark_session() over the REST (representational state transfer) API. The REST API is acceptable for small one-off queries. [src: pitfalls] Its /count endpoint often errors or times out on tables Spark handles instantly. [src: pitfalls] The /schema endpoint often times out on large tables, and DESCRIBE database.table through /query is more reliable. [src: pitfalls]

| Symptom | Meaning | Remedy |
|---|---|---|
| 504 Gateway Timeout | Query took too long | Simplify, filter, or use direct Spark [src: pitfalls] |
| 524 Origin Timeout | Server did not respond | Retry after a few seconds [src: pitfalls] |
| 503 "cannot schedule new futures after shutdown" | Spark executor restarting | Wait 30s, retry [src: pitfalls] |
| Empty response | Query failed silently | Check query syntax [src: pitfalls] |

## Type and SQL surprises between Spark and pandas

- Many databases store numbers as strings, including all kescience_fitnessbrowser columns and kbase_genomes coordinates and lengths. Cast before comparing, for example CAST(fit AS FLOAT) < -2. [src: pitfalls]
- Fitness Browser numeric columns, including fit, t, begin, end, cofit, rank, ratio and protein_length, are stored as STRING and need CAST(fit AS FLOAT) before any numeric comparison or ORDER BY. [src: pitfalls]
- Numeric Spark columns can arrive in pandas as strings through .toPandas(). [src: pitfalls] The report converts no_genomes, no_core and no_aux_genome with pd.to_numeric(..., errors='coerce'). [src: pitfalls]
- GC content and genome size from gtdb_metadata are string-typed and need a numeric cast. [src: gc_ecotype_ecology] The CheckM completeness and contamination columns of the quality flag are also string-typed, and all 293K genomes pass the flag. [src: gc_ecotype_ecology]
- Spark DECIMAL columns, such as abundance in kbase.nmdc_arkin.centrifuge_gold, arrive as decimal.Decimal after .toPandas(). [src: pitfalls] Mixing them with floats raises TypeError. [src: pitfalls] Cast to DOUBLE in SQL or use .astype(float). [src: pitfalls]
- The literal 1.0 is DECIMAL(2,1), so AVG(CASE WHEN … THEN 1.0 ELSE 0.0 END) also returns DECIMAL. [src: pitfalls]
- The rule of thumb is to wrap AVG() over integers or decimal literals in CAST(... AS DOUBLE), with .astype(float) after .toPandas() as a safety net. [src: pitfalls] The issue was seen in nmdc_community_metabolic_ecology NB03 for centrifuge_gold.abundance (cell-15) and gapmind_pathways AVG aggregates (cell-11/18). [src: pitfalls]
- np.random.choice() on Python strings returns numpy str_ objects, and createDataFrame() then raises PySparkTypeError. [src: pitfalls] Cast to native str first. [src: pitfalls]
- df.to_parquet on a Spark-Connect-derived pandas DataFrame fails with "Object of type PlanMetrics is not JSON serializable". [src: gc_ecotype_ecology] Rebuild the frame with pd.DataFrame({c: df[c].to_numpy() for c in df.columns}) to strip the Spark metadata. [src: gc_ecotype_ecology]
- Pandas DataFrames from Spark Connect .toPandas() have PyArrow ChunkedArray-backed columns, and passing them back to spark.createDataFrame() raises TypeError: Cannot convert pyarrow.lib.ChunkedArray to pyarrow.lib.Array. [src: pitfalls] This blocks the common pattern of pulling data to pandas, filtering it and registering it as a Spark temporary view. [src: pitfalls]
- The report recommends avoiding the pandas-to-Spark roundtrip by keeping filtering and joining in Spark SQL against the original tables, using the full bridge table name rather than a temporary view. [src: pitfalls] For small DataFrames that must go back to Spark, convert each column to native Python lists with df[col].tolist() before spark.createDataFrame(df). [src: pitfalls]
- Spark Connect rejects SELECT DISTINCT combined with an aggregate without GROUP BY (MISSING_GROUP_BY, SQLSTATE 42803). [src: pitfalls] This is a strict standard-SQL interpretation that differs from DuckDB and SQLite, which accept the syntax. [src: pitfalls] Use GROUP BY for grouped aggregations instead of SELECT DISTINCT col, COUNT(*). [src: pitfalls] It was seen in nmdc_community_metabolic_ecology NB03 cell-9 while checking gapmind_pathways score_category. [src: pitfalls]

## Tensions

- The discoveries digest advises autoBroadcastJoinThreshold = -1 to avoid UniProt broadcast failures. [src: discoveries] The agora report found the same setting harmful, with a notebook hanging 17+ min. [src: gene_function_ecological_agora] The quotes do not say which join NB10 ran in the discoveries case, so neither result is shown to be a general rule.
- Explicit BROADCAST hints cut presence-matrix extraction to ~274s from ~300s per organism in Smeli profiling, only an 8% improvement. [src: pitfalls] Another project reported ~210s per organism with broadcast hints. [src: cofitness_coinheritance] The quotes give different projects and setups, so the figures are not compared directly.

## Open Directions

- Benchmark joins with and without autoBroadcastJoinThreshold = -1 on uniprot_identifier and on mid-size tables. This would show when the setting helps and when it hurts.
- Measure the actual idle-kill threshold on JupyterHub with controlled sleep jobs. This would test whether ~17–25 min is a fixed scheduler limit.
- Rerun the Bacteroidota PUL neighborhood analysis with a full-Spark spatial filter that collects only per-feature aggregates. This would recover the deferred analysis.
- Rerun the ecotype analysis off-peak for all 456 eligible species, logging query time against cluster load.
- Test whether the Parquet read-back path stays under the result-size cap for results well above 1.5 GB.
- Time the presence-matrix extraction on a copy of the gene and junction tables partitioned by genome_id and gene_cluster_id. This would test how much scan time partitioning removes.
