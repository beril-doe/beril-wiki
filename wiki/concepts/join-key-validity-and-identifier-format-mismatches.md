# Join key validity and identifier-format mismatches

Schema-level join keys in the KBase Data Lakehouse define candidate bridges, but joins can still fail or silently return zero rows. A schema audit found 536 bridges from 29 keys. [src: berdl_data_atlas] The audit proves schema compatibility, not overlapping values. [src: berdl_data_atlas] Project-level pitfalls show the failure modes: composite keys, format mismatches, type mismatches and identical names with different meanings. [src: berdl_data_atlas, pitfalls] One format mismatch produced a false null result in the plant_microbiome_ecotypes analysis. [src: plant_microbiome_ecotypes] This page stops at taxonomic-name synonymy; see [[concepts/taxonomic-synonymy-and-strain-name-collisions-in-cross-database-matching]].

## Literature Context

The candidate papers describe identifier heterogeneity as a general obstacle to biological data integration. One review of in silico toxicology resources screened more than nine hundred databases against criteria that included interoperability or API access and appropriate identifiers. It also names the mapping and integration of databases into a common platform as an unmet need [PMID 31244651](https://pubmed.ncbi.nlm.nih.gov/31244651/). A federated-query study over Bgee, OMA and UniProtKB reports that syntactic and semantic heterogeneity between sources still blocks interoperability. Its answer was to define and formally describe explicit intersection points, or virtual links, among the three stores so that joint queries could run [PMID 31697362](https://pubmed.ncbi.nlm.nih.gov/31697362/). The SeMRA tool takes a related approach. It aggregates 43.4 million mappings from 127 sources and uses graph algorithms to infer missing mappings, while tracking provenance and confidence. The authors state that available mappings are incomplete and fragmented across resources [PMID 41021462](https://pubmed.ncbi.nlm.nih.gov/41021462/). A glycan workflow linking ChEBI, PubChem and GlyGen shows that cross-resource identifier connectivity often needs deliberate curation. Differences in how structures are represented limit what can be linked [PMID 34314492](https://pubmed.ncbi.nlm.nih.gov/34314492/). g:Profiler offers gene identifier mapping across 849 species as a service [PMID 37144459](https://pubmed.ncbi.nlm.nih.gov/37144459/). Work on annotating sample labels to ontologies with GPT models found that inconsistent annotation practices complicate integration. The best fine-tuned model reached 47-64% precision and 88-97% recall, and expert curation was still needed [PMID 40510764](https://pubmed.ncbi.nlm.nih.gov/40510764/).

The corpus is consistent with this literature in its main premise. Schema-level compatibility does not guarantee usable links. The 536 bridges from 29 keys in the BERDL Data Atlas (project id berdl_data_atlas) are candidates only, and value-space validity is established only for UC1. This parallels the literature's insistence that links be explicitly described and validated. It also parallels the observation that existing mappings are incomplete. The corpus's key lists and its recommended bridge tables, such as the omics_files_table and the gene_genecluster_junction path for ADP1, play the same role as the curated mappings and virtual links in those papers.

The corpus extends the literature in a practical direction. The candidate papers address semantic and ontology-level mapping. They do not report the failure modes this page documents. These include composite keys such as (orgId, locusId), GTDB prefix mismatches, integer versus string locusId, INT versus STRING bacdive_id, and the double-hyphen clade-ID parsing quirk. They also do not report the zero-row joins and silent organism drops these failures cause, or the false null result in plant_microbiome_ecotypes, where the NB12 H7 test showed 0/5 significant species until prefix repair gave 1306/1306 genome overlap. These Lakehouse-specific findings are novel relative to the candidates, which are abstracts only and do not discuss them. No candidate contradicts the corpus. None of them evaluates a normalizer library or a zero-row join check like the ones proposed in the open directions, so those remain untested against the literature.

## Schema-level candidate bridges

The linkage audit scanned 29 canonical join keys across genome, taxonomy, sample, annotation, pathway, biochemistry, protein, phage, literature and KBase workspace. [src: berdl_data_atlas] These keys define 536 schema-level cross-tenant bridges. [src: berdl_data_atlas] The 536 bridges are unordered and counted at (tenant × topic) cell granularity. [src: berdl_data_atlas] By tenant span, sample_id covers 10 tenants, genome_id 9, ncbi_taxon_id 9, feature_id 9 and ec_number 8. [src: berdl_data_atlas] Top bridges share up to 7 keys, for example kbase.pathway ↔ kescience.pathway and kescience.pathway ↔ phagefoundry.mobile_phage. [src: berdl_data_atlas] refdata.structural ↔ kescience.structural uses alphafold_pdb, pfam and protein_id. [src: berdl_data_atlas] The canonical bridge is whichever of genome_id, ncbi_taxon_id, sample_id and feature_id both sides expose. [src: berdl_data_atlas] The report offers a heuristic that analyses crossing topics, such as genome × phenotype × environment, almost certainly cross tenants. [src: berdl_data_atlas]

A schema bridge is only a candidate. The atlas shows that the schema admits a join, not that the values overlap, and value-space validity is established only for UC1 (use case 1). [src: berdl_data_atlas] The report describes UC1 as the first sample-validated synergy use case, with a corrected executable join recipe. [src: berdl_data_atlas] UC2–UC5 each need a first sample execution [src: berdl_data_atlas], and the report estimates about 15–30 min of SQL probing each. [src: berdl_data_atlas] The atlas also performs no across-tenant deduplication. [src: berdl_data_atlas] For example, refdata and kbase may hold the same UniProt entries under different cluster indices. [src: berdl_data_atlas]

The report supplies the key lists behind the atlas: per-key (tenant, topic, db, table) cells [src: berdl_data_atlas], per-key coverage statistics for 29 keys [src: berdl_data_atlas], and the 536 bridges with shared-key counts and key inventories. [src: berdl_data_atlas] Its linkage-atlas notebook ranks bridges by shared-key count. [src: berdl_data_atlas]

## Composite or missing keys

The proposed structural-fitness join assumed a protein_id column. Fitness Browser does not expose protein_id and uses a composite (orgId, locusId) key. [src: berdl_data_atlas] SQL probing found a working path: genefitness to besthitswissprot through (orgId, locusId), then to alphafold_entries through sprotAccession = uniprot_accession. [src: berdl_data_atlas] This was probed interactively in an on-cluster Spark Connect session. [src: berdl_data_atlas] Similarly, keggmember uses keggOrg/keggId and must be joined through besthitkegg. [src: discoveries] In the pangenome data, eggnog_mapper_annotations.query_name joins to gene_cluster.gene_cluster_id, not gene.gene_id. [src: pitfalls] The eggnog table uses query_name rather than a gene_cluster_id column. [src: pitfalls] For ADP1, cluster IDs share no strings with Lakehouse centroid IDs, a 0% direct match. [src: acinetobacter_adp1_explorer] The bridge runs through gene_genecluster_junction member gene IDs, which match feature_id in ADP1 pan_genome_features. [src: acinetobacter_adp1_explorer] That mapping is 100% complete but crosses 3 tables and may have edge cases where clusters split or merge. [src: acinetobacter_adp1_explorer] See also [[entities/adp1-to-pangenome-cluster-id-mapping]].

In NEON MAG work, members_id is an array<string> of contig IDs per MAG, and the KO table gene_id has the form <contig_id>_<start>_<end>. [src: neon_mag_functional_discovery] Equi-joining on the extracted contig portion connects gene KO calls to MAGs. [src: neon_mag_functional_discovery]

### Pangenome schema column differences

Key column names differ between pangenome tables. gene_cluster has gtdb_species_clade_id, not clade_name. [src: pitfalls] gapmind_pathways has clade_name. [src: pitfalls] gene has only gene_id and genome_id, with no species or clade column. [src: pitfalls] Gene-to-genome mapping therefore goes through the junction table, joining gene_genecluster_junction to gene on gene_id. [src: pitfalls]

### Table-specific primary keys

- **kbase_genomes.** All primary keys are CDM UUIDs. An external gene_id maps to internal IDs through name.name and name.entity_id. [src: pitfalls] There is no direct genome_id column. Genomes use contig_collection_id and can be cross-referenced through name or gtdb_taxon_id. [src: pitfalls]
- **PaperBLAST.** geneId spans RefSeq NP_*, UniProt-ish WP_*, VIMSS and other namespaces, so cross-namespace queries must go through seqtoduplicate. [src: pitfalls]
- **nmdc_arkin.** metabolomics_gold, kraken_gold, centrifuge_gold and gottcha_gold use file_id and file_name as primary identifiers, not sample_id. [src: pitfalls] Queries on sample_id raise AnalysisException: UNRESOLVED_COLUMN and stop notebook execution. [src: pitfalls] The report recommends file_id as the join key within the classifier and metabolomics tables. [src: pitfalls]
- **nmdc_arkin taxonomy_features.** It has no sample_id or file_id column. Its columns are numeric NCBI taxon IDs such as 7, 11, 33 and 34. [src: pitfalls] Selecting sample_id from it fails immediately. [src: pitfalls]
- **nmdc_arkin classifier-to-metabolomics joins.** Joining classifier tables directly to metabolomics_gold on file_id always returns zero rows, because the two sets use non-overlapping file_id prefixes. [src: pitfalls] Classifier files use nmdc:dobj-11-*. [src: pitfalls] Metabolomics files use nmdc:dobj-12-*. [src: pitfalls] The two are workflow outputs for the same biosample and link only through the biosample sample_id, such as nmdc:bsm-11-*. [src: pitfalls] The omics_files_table bridge has file_id, sample_id, study_id, workflow_type and file_type columns. [src: pitfalls]

## Identifier format mismatches

- **GTDB genome prefixes.** In cofitness_coinheritance, phylogenetic_tree_distance_pairs uses bare NCBI accessions, while genome, gene and gene_genecluster_junction use GTDB-prefixed IDs. Unnormalized joins to presence matrices gave zero matches. [src: pitfalls] Stripping the first 3 characters (GB_ or RS_) fixed this. [src: pitfalls] Overlap was then 100% for all tested species, including 399/399 for Koxy and 287/287 for Btheta. [src: pitfalls]
- **GapMind genome IDs.** kbase.ke_pangenome.gapmind_pathways stores genome IDs without the RS_ or GB_ prefix (for example GCF_001307155.1), while the pangenome genome table uses the prefixed form. [src: pitfalls] A direct equality match returns zero rows. [src: pitfalls] The report recommends stripping the prefix or using a fallback chain. [src: pitfalls] Its code tries the original ID, then the stripped ID, then an accession substring. [src: pitfalls] See [[entities/gapmind]].
- **BacDive accessions.** BacDive sequence_info.accession is GCA_*, while pangenome genome_id uses GB_GCA_* or RS_GCF_*. Prefix-match or strip prefixes before joining. [src: pitfalls]
- **Documented pangenome formats.** Pangenome genome_id uses RS_GCF_XXXXXXXXX.X (RefSeq) or GB_GCA_XXXXXXXXX.X (GenBank), with exact equality only. [src: pitfalls] gtdb_species_clade_id has the form s__<Genus_species>--<RS_GCF_XXXXXXXXX.X | GB_GCA_XXXXXXXXX.X>, for example s__Escherichia_coli--RS_GCF_000005845.2. [src: pitfalls]
- **Taxonomy IDs.** Joining pangenome genome to gtdb_taxonomy_r214v1 on gtdb_taxonomy_id returns zero rows, so join on genome_id. [src: pitfalls] genome.gtdb_taxonomy_id is truncated at genus level [src: pitfalls], while gtdb_taxonomy_r214v1.gtdb_taxonomy_id includes species. [src: pitfalls]
- **Locus tags.** Fitness Browser aaseqs uses RefSeq-style tags (e.g. ABZR86_RS*) for some organisms, while the gene table uses original tags (e.g. N515DRAFT_*). [src: discoveries] This caused a 0% merge rate for Dyella79, 1 of 34 organisms. [src: discoveries] The same project reports that aaseqs and gene-table locusIds had 0% overlap for Dyella79 and over 94% for other organisms. [src: pitfalls] Joining DIAMOND hits from aaseqs back to the gene table silently yields zero matches. [src: pitfalls]
- **Species clade IDs.** gapmind_pathways.clade_name stores the full gtdb_species_clade_id with the genome accession suffix, not the short GTDB_species name. [src: pitfalls] A join from a view built on GTDB_species returned 0 rows in nmdc_community_metabolic_ecology because the formats did not match. [src: pitfalls] The NB02 taxon_bridge.tsv already holds usable clade IDs. [src: pitfalls]
- **ModelSEED IDs.** In kbase_msd_biochemistry, IDs use a prefix-colon form such as seed.reaction:rxn00001 and seed.compound:cpd00001, not bare rxnNNNNN. [src: pitfalls]
- **UniRef100 to UniProt.** The kescience_alphafold join needs the UniRef100_ prefix stripped. This is a per-row string operation, so the report suggests materializing a mapping table for large joins. [src: pitfalls]
- **Category values (not an identifier).** Filtering metabolic_category == 'amino_acid' returns 0 rows. [src: pitfalls] The stored values are 'aa' and 'carbon'. [src: pitfalls]
- **Taxonomy ID columns (wrong value type).** Joining Fitness Browser organisms to gtdb_metadata by NCBI taxonomy ID gave zero matches. [src: pitfalls, metabolic_capability_dependency] The report states that the ncbi_taxid (or equivalent) column in gtdb_metadata holds the strings "t" and "f", not numeric IDs. [src: pitfalls]
- **Partial ID coverage (not a format difference).** Only 33.3% of Bakta's 17.6M distinct UniRef50 IDs exist in kbase_uniprot.uniprot_identifier. [src: discoveries]

Documented formats help avoid these errors. genome_id is RS_GCF_XXXXXXXXX.X or GB_GCA_XXXXXXXXX.X. [src: pitfalls] gtdb_species_clade_id is s__Genus_species--{representative_genome_id}. [src: pitfalls] gene_cluster_id is {contig}_{number} or {prefix}_mmseqsCluster_{number}. [src: pitfalls]

### A format mismatch that produced a false null result

In plant_microbiome_ecotypes, the NB12 null result for H7 (within-species plant-associated subclade segregation) was 0/5 significant across 5 species. [src: plant_microbiome_ecotypes] It was caused by a genome-ID format mismatch. [src: plant_microbiome_ecotypes] phylogenetic_tree_distance_pairs stores bare NCBI accessions (GCA_..., GCF_...), while genome_environment.csv uses GTDB prefixes (GB_GCA_..., RS_GCF_...). [src: plant_microbiome_ecotypes] After the merge, is_plant_associated was entirely NaN. [src: plant_microbiome_ecotypes] NB13 fixed this by prepending GB_ to GCA_ accessions and RS_ to GCF_ accessions. [src: plant_microbiome_ecotypes] Overlap became 1306/1306 genomes (previously 0), recovering 599 plant-associated genomes across the 5 tested species. [src: plant_microbiome_ecotypes] See [[concepts/within-species-subclade-segregation-of-plant-association-and-host-specialization]].

### Type mismatches

Matching identifiers can fail on data type alone, and the failure is silent.

- **locusId types.** In metal_specificity, fitness matrices use integer locusId indices (e.g. 206065), while Metal Atlas metal_important_genes.csv stores them as strings. [src: pitfalls] Pandas index lookup silently treats the gene as absent instead of raising an error. [src: pitfalls] This dropped DvH (495 metal-important genes) and Btheta (276 genes) from the analysis without warning. [src: pitfalls] The processing loop reported "SKIPPED (no fitness matrix or no non-metal experiments)" although the matrix existed. [src: pitfalls] The fix is to convert both sides to strings and to check output organism counts against the expected input. [src: pitfalls]
- **BacDive bacdive_id.** sequence_info.bacdive_id is INT, while isolation.bacdive_id is STRING. [src: pitfalls] A direct join returns zero rows because Spark does not implicitly cast across INT/STRING. [src: pitfalls] The report specifies CAST(si.bacdive_id AS STRING) = iso.bacdive_id. [src: pitfalls]

## Same name, different meaning

genome_id means a UPA in KBase, an accession in NCBI and a hash in MAG pipelines. [src: berdl_data_atlas] A shared column name is therefore not a shared identifier. In genotype_to_phenotype_enigma, 12 of 32 pangenome linkages via ncbi_strain_identifiers were incorrect genus matches. [src: pitfalls]

## Tooling quirks

Species clade IDs contain a double hyphen. [src: pitfalls] Direct Spark SQL handles it inside a quoted string literal. [src: pitfalls] The REST API rejects any query containing it, treating it as a comment and returning a 400 error. [src: pitfalls] Another report warns that the -- is parsed as a SQL line comment inside IN (...) clauses and recommends LIKE 's__Genus_species%' patterns instead of equality or IN. [src: pitfalls] The snipe_defense_system workaround queries all rows unfiltered and filters locally with pandas. [src: pitfalls]

## Open Directions

- Run value-space overlap probes for UC2–UC5, then compare the results to the schema-level bridge list. This would show how many of the 536 bridges return rows.
- Build a library of identifier normalizers (GTDB prefix stripping, clade-ID suffix handling, locus-tag reconciliation, type casting). Test each against every bridge that shares genome_id or feature_id.
- Add a check that flags zero-row joins and silently dropped organisms. Run it over past analyses to find other null results caused by plumbing, as in NB12.
- Run a deduplication audit of refdata versus kbase UniProt entries, to quantify the overlap that the atlas leaves unmeasured.
- Test ADP1 cluster mapping edge cases by looking for clusters that split or merge between the two pangenome analyses.
